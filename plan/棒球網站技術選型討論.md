# 台灣球員大聯盟網站 — 技術選型討論整理

## 專案背景

一個關於棒球的網站，初期規劃兩個核心功能，並預想了後續擴充方向。

**現有功能**
1. 記錄並呈現台灣球員在大聯盟的表現及數據（打擊/投球數據、球員基本資料、個人動態：所屬球隊賽程、是否受傷、上大聯盟或下放小聯盟等）
2. 介紹現代棒球的各個面向及專有名詞（大多為靜態內容）

**後續預想功能**
3. 爬取官網或社群新聞，呈現在網站
4. 專欄功能，請寫手發布針對台灣球員的文章、大聯盟規則更新消息等

**資料來源**：透過已知的 Python API 或自寫爬蟲取得數據。

---

## 後端框架：NestJS

**推薦理由**
- 專案會累積多種資料類型（球員資料、打擊/投球數據、動態、新聞、專欄），NestJS 的模組化設計讓各 domain 清楚分離，長期加功能不會越來越亂。
- 對熟悉 MVI 架構的人來說，NestJS 的 DI、Module、Controller/Service 分層非常直覺，幾乎零摩擦。
- TypeScript 原生支援佳，前後端可共用型別定義，省下大量對接與 debug 時間。
- 內建排程任務支援（`@nestjs/schedule`），適合定期爬取數據/新聞的需求。

**其他曾評估的選項**
- **Express**：最成熟、生態系最大、自由度高，但需自己搭配很多東西；適合小型專案 / prototype。
- **Fastify**：效能數一數二，schema-based 驗證佳；適合高吞吐量 API 服務。
- **Hono**：超輕量、支援多 runtime；適合簡單 API 或跨平台部署。

> 若覺得 NestJS 太重，Express + TypeScript 或 Fastify 也完全可行。但考量到已預想功能 3、4 的長期演進，前期多花點時間搭架構，後面加功能會輕鬆很多。

---

## Python 資料來源的架構建議

不需要把 Python 邏輯搬到 Node，較乾淨的做法是職責分離：

- **Python 端**：專心負責爬蟲 / 呼叫 MLB API（`pybaseball` 這類 library 生態成熟），把資料寫進資料庫或提供內部 API。
- **Node 端（NestJS）**：讀資料庫、組織 business logic、對前端提供 API。
- 兩者透過資料庫或內部 HTTP 溝通，各司其職。

---

## 前端框架：Next.js（React）

**推薦理由**
- **靜態 + 動態混合正好對到需求**：App Router 可針對不同頁面選不同渲染策略。
  - 功能 2（名詞介紹）、未來專欄 → 靜態生成（SSG）
  - 功能 1（球員數據）、功能 3（新聞）→ SSR 或 ISR（增量靜態再生）
- **SEO 重要**：公開內容希望被搜尋到，Next.js 的 SSR/SSG 對 SEO 遠優於純 SPA。
- **與 NestJS 型別共用**：可用 monorepo 抽出共用型別 package，改後端 API 時前端會在編譯期立即發現不一致。
- **熟 Compose 上手快**：Compose 的宣告式、狀態驅動 UI 思維和 React 幾乎一致。

**架構決策：後端要不要分開？**

1. **Next.js 全包**：前端 + 後端 API 都用 Next.js，Python 只負責爬資料進 DB。最精簡，適合初期。
2. **Next.js（前端）+ NestJS（後端）分開**：職責更清楚，後端邏輯複雜時比較好維護，適合長期演進。

> 建議：初期先用 Next.js 全包，等功能 1 數據處理、功能 3 定期爬取、功能 4 寫手權限等複雜度真的長出來，再把後端邏輯抽到獨立的 NestJS 服務。不用一開始就過度設計。

---

## 推薦的起步組合

| 層次 | 選擇 |
|---|---|
| 前端 / 後端 | Next.js (App Router) + TypeScript |
| 資料庫 | PostgreSQL（結構化數據多、關聯性強） |
| ORM | Prisma（TS 型別自動生成，也能與 Python 端共用 DB schema） |
| 資料抓取 | Python（`pybaseball`、爬蟲）寫入 PostgreSQL |
| UI | shadcn/ui + Tailwind |
| 部署 | Vercel（Next.js 原生支援，初期免費額度夠用） |

整個 web 這側都是 TypeScript，Python 只當純資料層，界線乾淨。

## 關於 UI 的可替換性

UI 這層相對最容易替換，但要分層次看，替換難度差很多：

**由易到難**
1. **元件庫樣式（Tailwind + shadcn/ui）→ 最容易換**
   - shadcn/ui 不是傳統 npm 黑盒套件，而是把元件原始碼直接複製到專案裡，元件就是「你的程式碼」，改樣式、換掉、刪掉都很自由，不會被套件綁死。
   - Tailwind 是 utility class，換色彩/間距/主題很直接。
2. **換整個元件庫（shadcn → MUI、Chakra）→ 中等**
   - 需改各元件寫法（props、className），但頁面邏輯、資料流、路由不用動。若有把 UI 元件包裝好，替換更輕鬆。
3. **換前端框架本身（Next.js → 別的）→ 最難**
   - 路由、渲染策略、資料抓取方式都綁在框架上，傷筋動骨。

**關鍵觀念：分層**

讓 UI 好替換的重點不在選哪個框架，而在把「業務邏輯 / 資料處理」和「呈現層」分開——就像 MVI 裡 UI 只是 state 的投影，business logic 不該知道 UI 長怎樣。

- 資料抓取、狀態管理獨立出來（custom hooks 或 server components）
- UI 元件盡量「笨」（只負責呈現，接 props、發事件）

維持這個界線，換 UI 樣式或元件庫時，動到的範圍就會被限制在呈現層，核心邏輯不受影響。因此用 shadcn/ui + Tailwind 起步很安全：它本身就是最好替換的那種，加上保持分層乾淨，未來彈性很大。
