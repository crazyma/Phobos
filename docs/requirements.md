# 產品需求文件（PRD）— 台灣球員大聯盟網站

<!--badges: 類型=產品需求; 對象=台灣棒球迷; 版本=v1 範疇; 語言=繁體中文-->

> 從**產品／服務面**描述這個服務要解決什麼、為誰做、提供哪些具體功能。技術「用什麼、為什麼」見 `adr/decisions.md`；欄位級規格見 `spec/`。本文件是那兩者的上游。

---

## 1. 產品定位

一個**繁體中文**的網站，讓台灣棒球迷能在**同一個地方**追蹤台灣球員在美國職棒（大聯盟與 3A／2A 小聯盟）的表現與動態，並附帶介紹現代棒球的規則與數據名詞。

- **一句話**：台灣球員在美職的中文戰情室 + 棒球知識入口。
- **背景**：初期為開發者的個人／學習專案，但產品目標對真實使用者（台灣球迷）有價值，設計以使用者需求為準，而非只當練習。

---

## 2. 目標使用者

| 使用者類型 | 特徵 | 主要需求 |
|---|---|---|
| **關注型球迷**（主要） | 平常追某幾位台灣球員，想知道「他最近如何、上大聯盟了沒、有沒有受傷」 | 快速看到球員近況、動態、數據，中文、不用翻英文網站 |
| **數據型球迷** | 想看較完整的打擊／投球數據、跨球季比較 | 結構化、正確、可比較的數據呈現 |
| **入門球迷 / 路人** | 看比賽或新聞時遇到不懂的名詞（wRC+、FIP、IL…） | 用中文快速查到名詞／規則的白話解釋 |

> 開放問題：主要客群偏「關注型」還是「數據型」會影響數據呈現的深度，需你定調（見 §9）。

---

## 3. 使用者面臨的問題（為什麼需要這服務）

1. 台灣球員散布在不同球隊、不同層級（大聯盟／3A／2A），資訊分散在多個英文網站，**沒有一個中文的集中處**。
2. 官方英文數據網站對一般球迷**門檻高**（語言、名詞、資訊過載）。
3. 球員的「動態」（升上大聯盟、被下放、交易、進傷兵名單）**常常臨場才公布、且不易一眼看到時間軸**。
4. 遇到現代棒球名詞（進階數據、規則）時，**缺乏中文、簡潔可信的解釋**。

## 4. 產品範疇

### 4.1 這一版要做（v1）

- **功能一：台灣球員追蹤**（動態內容）
- **功能二：棒球規則／名詞介紹**（靜態內容）

### 4.2 設計上預留、這版不做

- **功能三：新聞**（爬取官網／社群新聞並呈現）
- **功能四：專欄**（寫手發布針對台灣球員的文章、規則更新消息）

### 4.3 明確不在範疇（v1）

- 逐球（pitch-level）等級的細部數據與圖表
- 使用者帳號、留言、社群互動
- 即時比分推播 / 通知訂閱（可能列入 future）
- 付費 / 會員機制

## 5. 功能需求（具體描述）

### F1. 台灣球員追蹤

追蹤名單為**人工維護的台灣球員白名單**（歷史上台籍美職球員僅十幾位，可控）。成績**涵蓋所有能抓到資料的層級**——從大聯盟、3A、2A，一路到 1A、新人聯盟；只要來源有資料就呈現（多數台灣球員剛進體系、主要在低階層級，若只做高階幾乎沒東西可看）。升降／異動涵蓋所有層級。

#### F1-0 首頁（動態導向）
首頁以「最近發生 + 即將發生」為主軸，**不放全員名冊**：

1. **最近 24 小時**（主）：這段時間內的**比賽結果**與**球員動態**（升降 / 交易 / 傷兵進出等），彙整成動態流／摘要。
2. **即將發生**（次）：球員所屬球隊的**下一場比賽**資訊（對手、時間）。

- **球員名冊**不佔首頁主體，改放在 **top bar / side bar 的導覽入口**；名詞介紹（F2）同樣從全域導覽進入。
- 動態中的單場數據沿用 §7.2「今日快訊＝單場精簡」。
- 「24 小時」為顯示概念，實際資料隨一天兩次同步更新（見 F1-3）。

> 使用者故事：作為關注型球迷，我一打開網站就想看到「這一天發生了什麼、我關注的球員接下來何時出賽」，不用自己一個個點。

#### F1-1 球員總覽頁
- 從全域導覽（top bar / side bar）進入；列出所有被追蹤的台灣球員。
- 每位球員以卡片／列呈現**一眼可懂的近況**：目前所屬球隊、所在層級（大聯盟／各級小聯盟）、目前名單狀態（出賽中／傷兵／小聯盟）、以及一項近期表現摘要。
- 可依「目前層級」「球隊」等排序或篩選（細節待定）。

> 使用者故事：作為關注型球迷，我想在一頁看到所有台灣球員現在人在哪一隊、哪一層、狀態如何，不用一個個查。

#### F1-2 球員個人頁
單一球員的完整戰情，分四區：

1. **基本資料**：中英文名、守備位置、打擊／投球慣用手、生日、目前所屬球隊與層級、目前名單狀態。
2. **球季數據**：依球季、依層級（大聯盟到小聯盟各級）呈現**標準季賽數據 + 一組進階數據**（明細見 §7.3）；資料**從 2020 球季起**（未來可往前補）。低階層級資料可能稀疏，抓得到就顯示。
3. **動態時間軸**：升上大聯盟 / 下放小聯盟 / 交易 / 進出傷兵名單 / 被 DFA、釋出等異動，**依時間排序成時間軸**，讓人看得出「什麼時候發生什麼」。
4. **所屬球隊賽程**：該球員目前球隊的近期與即將到來的賽程與比分。

> 使用者故事：作為球迷，我想在球員頁看到他這季打得如何、最近有沒有被升降或受傷、他隊上接下來打誰。

#### F1-3 資料新鮮度
- 每頁需標示**資料最後更新時間**，讓使用者判斷新鮮度。
- 更新頻率為**一天兩次**（早上結算前一天賽果與累計數據；傍晚同步當日賽程、異動與傷兵名單）。

### F2. 棒球規則／名詞介紹

使用者通常是**在站內或站外看到某個名詞、想搞懂它**才點進來——目標是**幫他讀懂當下的脈絡**，而非教科書式從定義講起。

#### F2-1 涵蓋範圍（逐步累積）
- **v1 優先：數據名詞**——先把球員頁會用到的 6+6 進階數據與常見標準數據講清楚（wRC+、FIP、OPS、WHIP、IL、DFA、waiver…），起手約 **20~30 則高頻名詞**（6+6 為必做核心）。
- **第二批：基本規則**（好球帶、盜壘、犧牲打…）。
- **更後面**：戰術／玩法、規則更新消息。
- 靜態內容、逐步新增；撰寫採 **AI 輔助草擬 + 人工校訂**。

#### F2-2 單頁內容結構（解讀優先）
每則名詞頁由上而下三層，重點在「怎麼幫使用者判讀」：

1. **主要（最上、最顯眼）——「這在看什麼、怎麼判讀」**
   - 一句白話點出它衡量什麼。
   - 數值大概的分布範圍。
   - **級距對照**：哪個區間算及格／不錯／厲害／MVP 等級。← 這頁的主角。
2. **次要（下方、字級較小）——名稱與算法**：中英文名、定義、計算方式；**點到為止，不必像 wiki 那麼細**。
3. **延伸（最後）——原始權威來源**：附 MLB／Baseball Savant 等原始介紹頁連結，讓想深鑽的人自己去讀。

> 範例（OPS）：先講「衡量打者整體進攻能力，聯盟大致落在 .600~1.000，.800 算不錯、.900 以上明星級、破 1.000 是 MVP 等級」；下方小字補「OPS = 上壘率 + 長打率」；最後給 MLB 官方說明連結。

#### F2-3 與球員數據雙向連結
- 球員頁上的數據（如 wRC+）可**點進對應名詞頁**；名詞頁亦可回連範例球員，形成 F1×F2 整合。

#### 其他
- 以**主題分類**組織，內容可瀏覽、（理想上）可搜尋。

> 使用者故事：作為入門球迷，我在文章看到「OPS .950」不懂算好算壞，點進名詞頁一眼就知道「這是明星等級」，不用先看公式。

## 6. 非功能需求

| 面向 | 需求 |
|---|---|
| **語言** | 介面與內容以**繁體中文**為主；球員英文原名保留以利對照。 |
| **SEO** | 公開內容（球員頁、名詞頁）需能被搜尋引擎索引；使用者常從 Google 搜球員名／名詞進來。 |
| **裝置** | 響應式設計，**手機優先**（球迷多在手機上看）。 |
| **效能** | 頁面載入要快；靜態知識內容尤其應接近即時。 |
| **正確性** | 數據來自可信來源；上游若事後修正，網站數據**需跟著更新**（不是抓一次就固定）。 |
| **可用性／韌性** | 即使背後資料同步暫時失敗，網站仍能顯示既有內容，**不因資料層問題而整站不可用**。 |

## 7. 內容 / 資料呈現需求（產品視角）

### 7.1 動態與狀態

- **球員動態類型**（要能呈現）：升上大聯盟、下放小聯盟、交易、被指定轉讓（DFA）、釋出、進／出傷兵名單。
- **名單狀態**（要能呈現）：出賽中（active）、傷兵名單（IL）、小聯盟（minors）等，並保留**歷史**以畫出時間軸。
- **層級標示**：清楚標明每筆成績屬於哪一層級（大聯盟／3A／2A／1A／新人聯盟…），避免混淆。

### 7.2 數據呈現深度依「情境」而不同

數據深度不是單一答案，依出現的頁面/情境決定：

| 情境 | 深度 | 內容 |
|---|---|---|
| **今日快訊**（單場，如首頁快訊卡） | 精簡、單場 | 打者：打席、安打、全壘打、打點、保送、三振。投手：局數、被安打、失分、自責分、三振、保送。「一眼看完今天幹了啥」。 |
| **球員頁** | 標準季賽數據 + 一組進階數據 | 見 §7.3。 |

### 7.3 球員頁的數據分層

- **標準季賽數據**：一般球迷看得懂的常見數據。
  - 打者：AVG / OBP / SLG / OPS、HR、RBI、SB、BB、SO…
  - 投手：ERA、**WHIP**、IP、K、BB、W-L、SV、HLD…（WHIP 為未校正的簡單比率，歸此層而非進階）
- **進階數據（可調整清單，不寫死）**：先挑 6 個打者、6 個投手當起點，之後持續增減／替換（呼應棒球演進）。

  **打者 6 進階**

  | 指標 | 說什麼故事 |
  |---|---|
  | `wRC+` | 校正球場/聯盟後的綜合打擊，100=聯盟平均（頭號指標） |
  | `wOBA` | 加權上壘率，整體攻擊產出 |
  | `ISO` | 純長打率（SLG−AVG），power |
  | `BB%` | 保送率（選球眼） |
  | `K%` | 三振率（接觸/選球風險） |
  | `WAR` | 打擊+跑壘+守備的單一總值 |

  **投手 6 進階**

  | 指標 | 說什麼故事 |
  |---|---|
  | `FIP` | 獨立防禦率，排除守備/運氣，比 ERA 更貼近真實 |
  | `K%` | 三振率（宰制力） |
  | `BB%` | 保送率（控球） |
  | `HR/9` | 每 9 局被轟（長打壓制） |
  | `LOB%` | 殘壘率（危機處理/運氣，判斷 ERA 是否回歸） |
  | `WAR` | 投手綜合價值單一數字 |

  - **口袋替補**（日後想換時）：打者 `BABIP`、`OBP`；投手 `xFIP`、`SIERA`、`WHIP`。
  - **可用性**：進階數據多在 MLB / 高階小聯盟才齊全（wRC+/WAR/FIP 需聯盟/球場係數）；低階層級算不出來就**不顯示**（best-effort）。

## 8. 成功樣貌（v1 做到什麼算成功）

- 名單內**每一位**台灣球員，都能在站上看到：他現在在哪隊哪層、目前狀態、本季主要數據、最近的升降／傷兵動態。
- 使用者能在**一頁**看懂某位球員的近況，不需再去英文網站。
- 常見棒球名詞能用中文查到解釋。
- 球員頁與名詞頁能被 Google 搜到。

## 9. 產品決策

> 產品面決策，與 `spec/` 的技術未決項不同。

### 9.1 已定

- ✅ **主要客群**：兩者兼顧、**關注型優先**——預設呈現簡潔近況與動態，進階數據可展開或放次要位置。
- ✅ **首頁形態**：**動態導向**——主軸為最近 24 小時（比賽結果 + 球員動態），其次為即將發生（下一場比賽）；球員名冊改放全域導覽（top / side bar）入口，不佔首頁主體（見 §5 F1-0）。
- ✅ **數據呈現深度**：依情境分層（見 §7.2 / §7.3）——今日快訊用單場精簡；球員頁用標準季賽數據 + 6 打者/6 投手進階數據（可調整清單）。WHIP 歸標準層。
- ✅ **圖像素材**：**只放球隊 logo，不放球員照片**（避開球員肖像權）。
- ✅ **名詞／規則內容**：v1 以數據名詞優先（起手 20~30 則、6+6 必做）、逐步累積、AI 輔助草擬+校訂；單頁採**解讀優先**三層結構（判讀/級距 → 定義算法小字 → 權威原始連結）；與球員數據雙向連結（見 §5 F2）。
- ✅ **語言**：**中文為主 + 英文原名輔助**（球員／球隊附英文名對照），不做全站雙語。
- ✅ **通知／訂閱**：**列為 future，v1 不做**（需帳號系統；見 §4.2、§4.3）。
