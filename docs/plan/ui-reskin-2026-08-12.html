UI 拉皮研究 — 以 Phobos-UI 雜誌風設計改寫前端（2026-08-12）

研究外部設計專案 Phobos-UI（v0 產出、雜誌跨頁風格，自帶設計指南頁）能否用來改寫本站前端。結論：技術棧同源、可直接搬，但設計覆蓋的資訊深度只有現行的一部分，且與 PRD 的「不放球員照片」決策正面衝突。
本文只做研究與對照，不含實作切片。四個待決項（§5）拍板後再開票到 .scratch/ui-reskin/issues/。

類型 研究/選型輸入 Phobos-UI repo（v0 設計專案）對象 spec-02 既有五頁狀態 待決四題、未動工

一句話結論

搬的是 design token 與版面樣板，不是元件庫——設計專案通篇手刻 Tailwind，@/components/ui/* 的 import 數是 0。因此拉皮的成本不在依賴，在於補齊設計沒畫到的那些頁面區塊，以及先解決球員照片這個產品決策衝突。

2.1 首頁

  • 設計：大標 → 封面人物跨頁（大圖＋人物簡介＋四格數據）→ 近期賽果 → 異動快訊。
  • 我們（components/home/home-page.tsx）：最新賽況 → 球員動態 → 即將出賽 → 外加整套 emptyState（休賽季的本季／上季回顧＋名詞推薦）。

設計缺：即將出賽整區、emptyState 整套。前者是 PRD §9.1 已定的功能。

設計多：封面人物需要 headshot + summary（人物介紹段），DB 兩個欄位都沒有。

2.2 球員名冊

  • 設計：依 MLB/3A/2A 分區，每區標題列＋人數；卡片有編號浮水印、頭像、三格數據。
  • 我們：層級下拉 + 排序下拉 + archived 折疊區；卡片有「狀態一句話」與「近況一句話」。

設計缺：篩選／排序 UI、archived 區、狀態一句話的位置。

設計多：頭像、編號浮水印。

2.3 球員個人頁（差距最大）

設計 7 區：返回列 → hero → 檔案資訊（摘要＋4 格 dl）→ 近期比賽紀錄（StatList）→ 近況走勢 sparkline → 媒體與新聞集錦 → 本季數據（StatCards）→ 逐季歷史表 → 個人動態。

我們 5 區（spec-02 §2.3）：hero → 球季數據 → 逐場成績 → 動態時間軸 → 出賽預告。

設計缺：

  • 出賽預告整區（下一系列賽、確定先發／可能出賽／傷兵中、台灣時間、近期戰績）——無任何對應樣板。
  • 進階數據展開區（components/player-detail/season-stats.tsx:132 的 <details>，每項連回名詞頁）。
  • 完整數據表的資訊量：我們打擊 20 欄、投球 20 欄（season-stats.tsx:24-68），另有 per-team 分列＋合計列＋「低階層級數據僅供參考」註記。設計的 StatCards 一個層級只放 4 個大數字——這不是樣式差異，是差一個量級，需要「4 格重點 + 可展開完整表」的折衷。
  • archived 球員的「已離開美職體系／生涯總成績」模式。

設計多：媒體與新聞集錦（news/thread/tweet/video ＋縮圖，無資料來源）、sparkline 走勢（需 0-100 的 form 序列，無此資料）、人物 summary。

2.4 名詞（架構性衝突，非樣式問題）

  • 設計：單頁 /magazine/glossary，搜尋框 + 分類分區 + 卡片，點卡片開 modal。
  • 我們：/glossary 索引 + 每則獨立 /glossary/[slug] 靜態頁（dynamicParams = false、24 則 MDX）。

⚠️ 全面 modal 化會直接砸掉 SEO。requirements.md §8 成功樣貌寫明「球員頁與名詞頁能被 Google 搜到」，app/glossary/[slug]/page.tsx 也有 generateStaticParams ＋ OG metadata。

建議：保留獨立頁，把設計 modal 的內容結構當成名詞頁的版面骨架。設計的五段（簡述概念／對球員的意義／數據高低／站內相關／延伸參考）與我們 spec-04 的四層（判讀 → 定義算法小字 → 延伸 → 範例回連）大致對得上，只多出「簡述概念」條列。索引頁則採用設計的搜尋框＋卡片牆。完整取捨與 A→B 執行順序見 §5.3。

5.3 名詞頁 modal vs 獨立頁

決議方向：先 A、把 B 當後續 polish。（2026-08-12 討論）

問題不是「modal 不好」，而是「只有 modal」會拿掉 24 個可被索引的 URL。設計那頁的 modal 是純 client state：卡片是 <button>（glossary-page.tsx:204），詳解在 if (!rendered) return null（:273）之後才存在。

#### 會掉什麼

現在有modal-only 之後
24 個 /glossary/[slug] 靜態頁1 個 /glossary
每則獨立 title／description／OG／Twitter（app/glossary/[slug]/page.tsx:24-39）只剩索引頁一張通用卡
sitemap 24 條（lib/seo/sitemap.ts:12-14）0 條
站內有真連結指向每則名詞卡片是 <button>，爬蟲走不進去

長尾查詢是名詞庫的主要獲客路徑——「wRC+ 是什麼」「FIP 中文」本來一頁精準對一題，全塞進一頁後 24 個主題互相稀釋。

排除一個看似可行的補救：把 24 份詳解都 SSR 進 DOM 再用 CSS 藏起來——不管用。索引單位是 URL 不是 DOM 片段，隱藏內容還會被降權。

#### 比 SEO 更硬的一條

名詞頁不只是 SEO 資產，它是兩個機制的掛載點：

  1. 雙向連結（spec-04 §D）：components/player-detail/season-stats.tsx:150 的進階數據每項都連 /glossary/${metricSlug(key)}。名詞頁沒了，這些連結沒有去處。
  2. build-fail 護欄：getRegistry() 在 app/glossary/[slug]/page.tsx:51 被呼叫，build 時只要有顯示中的 metric 缺名詞頁就炸。這道「名詞頁先行」的保險是掛在名詞頁的 render 上的。

而 requirements.md §8「球員頁與名詞頁能被 Google 搜到」是驗收條件，不是偏好。

#### 但設計師的判斷不是錯的

在索引頁掃過 24 張卡、想確認某則、看完回到原位——這個情境用整頁跳轉確實比較差。modal 解的是真問題，只是不能是唯一入口。

#### 三個選項

做法評價
A（先做）索引頁採用設計的搜尋框＋卡片牆，卡片是真 <Link>，點擊進 /glossary/[slug] 全頁；全頁版面用 modal 那五段骨架（簡述概念／對球員的意義／數據高低／站內相關／延伸參考）SEO 零風險、最快看到成果；失去「不離開索引頁」的閱讀感
B（後續 polish）Intercepting routes：卡片一樣是真 <Link>，加 app/@modal/(.)glossary/[slug]/page.tsx 攔截 client-side 導航顯示 modal；直接輸網址／重新整理／爬蟲則走原本全頁。同一份 MDX body 兩邊共用，URL 也會變（可分享、可回上一頁關閉）兩全。代價：root layout 要加 @modal slot；設計的雙 rAF 進場動畫要改寫（route 切換本身已延遲一拍）。⚠️ 未實測 intercepting route 配我們 await import(...content/glossary/${slug}.mdx) 的動態 MDX 匯入在 Next 16 的行為 → 開票前需一次小 spike
C索引頁 modal 只放「預覽＋看完整說明」按鈕，深度內容仍在全頁兩邊都不夠好，不建議

順序理由：拉皮的價值主要在視覺，modal 是錦上添花。先把 24 頁的版面換成設計骨架、索引頁補上搜尋與分類卡片牆，是風險最低的一刀；視覺落地後再花一張票做 B，spike 失敗也只是退回 A，不擋主線。
